# 项目说明

## 简介

一个不需要服务器的局域网聊天工具：在同一局域网内启动客户端，用户可以主动搜索局域网内的其他在线用户，选中后便可以与对方点对点连接并进行聊天交流。

## 项目目标

### 核心目标

1.再同一局域网内，用户可以通过客户端发现其他在线用户

2.发现后能够选择某个用户，建立点对点 TCP 连接

3.双方能够进行基本的文字消息收发

4.整个工具不依赖中心服务器、不依赖数据库、不依赖第三方网络框架

### 第一阶段目标

先做终端版，只实现最小闭环

1.启动时指定昵称、发现端口、聊天端口

2.能够主动搜索在线用户

3.能够展示搜索到的用户列表

4.能够选择某个用户并进入一对一文字聊天

5.能够正常退出

## 核心设计思路

### 1.发现与聊天分离

工具分成两层：

**发现层**：使用 UDP，负责“找到谁在线”；

**聊天层**：使用 TCP，负责“建立连接并收发消息”。

发现端口和聊天端口分开，互不干扰。

### 2.广播主动探测

发现方式采用主动探测：

用户触发“搜索”时，客户端向局域网广播一条探测请求；

其他在线客户端收到后，单播回复自己的昵称和聊天端口；

发起方在短时间内收集回复，形成在线用户列表。

### 3.单播回复

收到探测请求的客户端，只向发起方单播回复，不向全网广播，避免多台设备互相刷屏。

### 4.单机单实例

一台机器只运行一个客户端实例。通过绑定固定的发现端口来实现：端口被占用时提示退出，避免同一台机器多个实例互相干扰。

### 5.先不处理复杂网络环境

第一阶段明确不处理：

跨子网；

AP 隔离；

NAT 穿透；

公网通信。

先假设设备处于同一个简单局域网内，能够收到 UDP 广播。

## 典型使用流程

1.用户启动客户端，输入昵称，程序监听固定 UDP 发现端口和 TCP 聊天端口；

2.用户输入“搜索”命令；

3.客户端向局域网广播探测请求；

4.其他在线客户端收到请求后，单播回复自己的信息；

5.发起方收集回复，展示在线用户列表；

6.用户选择某个用户，客户端用对方回复中的 IP 和聊天端口建立 TCP 连接；

7.双方通过 TCP 连接发送和接收文字消息；

8.用户退出聊天或退出程序。

## 功能范围

**MVP 包含**

1.设置昵称；

2.UDP 主动探测发现；

3.单播回复；

4.在线用户列表展示；

一5.对一 TCP 文字聊天；

6.单机单实例限制；

7.基本错误处理：坏消息不导致程序崩溃。

**MVP 暂不包含**

1.群聊；

2.文件传输；

3.消息历史持久化；

4.用户账号和身份认证；

5.消息加密；

6.图形界面；

7.跨公网通信；

8.NAT 穿透；

9.多设备同时多实例。

这些可以作为后续扩展，不进入第一版。

## 技术选型

开发语言：Python 3；

网络通信：Python 标准库 socket；

并发处理：threading，用于后台监听发现请求和 TCP 连接；

消息格式：JSON，使用 json 模块编解码；

节点与请求标识：uuid；

命令行参数：argparse；

开发环境：VS Code 或 PyCharm；

测试工具：多终端窗口、可选 Wireshark、系统端口查看工具；

不引入：WebRTC、libp2p、数据库、消息队列、后端框架。

## 模块划分

计划按职责分层:

protocol.py：定义消息格式、构造消息、解析并校验消息；

discovery.py：UDP 发现层，负责监听探测请求、单播回复、发送广播并收集结果；

chat.py：TCP 聊天层，负责服务端接受连接、客户端连接、消息收发；

cli.py：命令层，负责读取用户输入、解析命令、调用发现层和聊天层；

main.py：程序入口，解析参数、创建共享状态、启动各模块、进入命令循环。

依赖方向是单向的：main → cli → discovery / chat，发现层和聊天层互不依赖。

## 开发计划

先完成消息格式定义，确保构造和解析能往返验证；

完成 UDP 发现层，用两个终端实例验证互相发现；

完成 TCP 聊天层，用本机端口验证消息收发；

完成命令层和入口，把发现与聊天串起来；

用两台真机在同一局域网内验证发现和聊天；

补充单实例限制、坏包处理和基本提示信息。

## 验收标准
第一版完成后，至少满足：

同一台机器上，两个不同发现端口的实例可以互相发现；

两台真机连接同一局域网时，可以互相发现；

发现后可以建立 TCP 连接并互发文字消息；

收到非法或格式错误的消息时，程序不崩溃；

同一台机器重复启动第二个实例时，能够给出明确提示并退出；

不依赖任何服务器即可完成上述流程。

## 风险与限制
广播可能被屏蔽：部分企业 Wi-Fi 或公共网络开启 AP 隔离，设备之间收不到广播。第一版不处理，必要时后续增加手动指定 IP。

防火墙可能拦截：Windows/macOS 首次监听端口时需要放行。

广播不能跨子网：第一版只面向同一子网。

TCP 是字节流：消息需要约定边界，第一版计划用换行分隔。

无加密、无认证：第一版只适合可信局域网环境。

在线列表是搜索时刻的快照：对方下线不会自动更新，下次搜索才会反映。

## 预期成果
第一阶段交付一个可运行的终端聊天工具：无需服务器，启动后可以主动搜索局域网内的其他用户，选择用户后直接进行一对一文字聊天。它既能验证“局域网 P2P 发现 + 直连通信”的核心思路，也为后续增加图形界面、文件传输或加密能力留下清晰的扩展空间。
